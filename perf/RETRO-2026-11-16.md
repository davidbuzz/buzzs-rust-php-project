## The five moves that produced the wins

They repeat across the tape series (`8f147a16` .. `e642f664`, then `7753e5c9`), and each one is
re-usable on its own:

1. **Pre-decode once per loop, specialize per site** — the tape carries instructions that are
   ready to run instead of re-decoding the opcode each round (`8f147a16`).
2. **Move cold paths out of line** so the hot path pays nothing for them — `bd05a529`
   ("every out-of-line tape handler is called with the frame alone"), `75c502c4`, `741f76d3`.
3. **Store results in place** into the consumer's folded slot instead of through a temporary —
   `eacf0011`, `d08111b6` ("results stored in place"), and on the return path `0f0b3a28`.
4. **Fast paths must decline, and say so** — each dims/props/scalar fast path documents its
   decline conditions and falls back to the generic op (`f8426f91`, `f1bc66c0`, `065f7bfd`), and
   the specialized arithmetic is cross-checked operator-by-operator against the generic
   implementation in a unit test (`e642f664` vs `exec::num_bin`).
5. **A measured loss is reverted as its own commit** — `3891e18c` ("revert the AssignT string
   move: measured 1.7% slower on `$x = $s[0]`, no gain elsewhere"), `31323a5a` ("undo the
   slowdowns of the dims/props tape families").  This is why the tape is not a pile of
   accidental regressions, and why the message convention records the number that killed it.

## What we knew and did not act on

The 13 Nov review notes flagged, under the opcode-shape change:

> `dce_drops_foreach_over_empty_literal_array` — **more than stale**: the foreach-over-`[]`
> drop is no longer applied … Likely a genuine optimization regression; investigate.

Three days later the same hole shows up as eight failing PHPTs (`opt/dce_001`, `dce_003`,
`dce_004`, `dce_005`, `dce_007`, `dce_008`, `dce_009`, `opt/sccp_002`) plus the
`opt/*` cluster in the fresh baseline diff.  Two habits follow:

- A review finding marked "behaviour change, investigate" gets fixed before the next perf
  step, not filed.
- When the compiler changes opcode shapes, the optimizer tests that assert on opcode variants go
  stale and hide real losses.  Re-baselining is only safe once the fold has been shown — in a
  dump — to still fire.

## Measurement traps we hit (each one cost a detour)

- **One `perf stat` window, two builds**: measuring candidate and reference back-to-back inside a
  single window produced a fabricated 31.32 vs 33.28 difference and a wrong conclusion.  Each
  build gets its own invocation.
- **`git stash -u` around a baseline the harness reads**: it took `perf/bench/goal.tsv` with it,
  so a 420M-rep run died mid-flight.  Stash the source, not the measurement inputs.
- **The 5% noise threshold is too loose for 2–3% steps**: decide with one good run, then A/B the
  candidate against the reference, not against yesterday's number.
- **A bisect keyed on test failures can point at the wrong commit**: the search that named
  `9f92f769` as "first bad" for the dead-code hole was wrong — its parent `33ca7cfd` emits
  byte-identical ops, both keep the dead chain, so the cause sits outside the window (the tests
  also depend on the ArgInfo table, which is a second changing variable).
- **Sparse and full php-src trees are not interchangeable for PHPT**: 258 skipped tests became
  429 in a tests-only tree (the ones that read non-test files).  And `phpt-runner` resolves
  `phpt-scope.txt` by walking up from the test root, so an external tree silently picks up
  whatever scope file sits above it — pass `--scope` explicitly.
- **A recovered summary is not evidence**: two "known facts" carried forward from notes (which
  patch won `prop_read`, and when the DCE hole appeared) were both wrong once the commits were
  built.  Re-verify a claim against a build before building on it.

## The kit

`perf/bench/harness.py` and `irun.sh` (deterministic user-space instruction counts, ~0.1%),
`goal.tsv` + `scripts/acceptance.sh` (one acceptance number, regenerated by `acceptance.py
--record`), `compare.sh`, `ops.sh`, `table.sh`, `slowtests.sh`, `profile.sh` (flat profile plus
cost categories via `categorize.py`).  The A/B reading rules are in
[README.md](README.md); the C reference counts are pinned in `goal.tsv`.

New in this retro: **`perf/bench/lines.sh <php-binary> <script.php> [reps] [top]`** — a
source-line histogram of one run.  `perf report` buckets by symbol, which is too coarse inside an
interpreter loop or a call path; the number we act on is usually one line.  It needs the same
`sudo -n perf` permission as the rest of the kit.

## The lead it leaves behind

`zend:userfunc` is entirely on the tape — the specialized call family (`TOp::CallInit` /
`CallSend`, `calls::prepare`/`send`/`enter`) does run — so the remaining 5.9x is not a missing
family, it is that the call machinery itself costs about five times what C's costs.  Sampled on
instructions (`perf record -e instructions:pp`) over 3M repetitions:

| share | symbol |
|---|---|
| 30.6% | `exec::tape::run_tape` (the tape loop itself) |
| 21.7% | `call::return_simple` |
| 17.0% | `exec::tape::run_call` |
| 9.8% | `exec::tape::calls::enter` |
| 8.6% | `exec::tape::calls::send` |
| 8.4% | `exec::tape::calls::ready_frame` |

Against the empty loop, one call of `g(1) { return $x; }` costs us ~675 user instructions where
C spends ~133 (and kernel instructions are not the difference: 1.7% of ours, 9.8% of C's).  So
the next step is not more tape coverage but making the per-call work proportional: the return
path (`return_simple`, a fifth of the whole workload for a function that returns its parameter)
and frame preparation (`ready_frame`) are the two fattest places, and `run_tape` at 31% says the
loop's own dispatch still needs the same treatment the arithmetic families got.
